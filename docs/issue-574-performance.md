# Issue #574：白屏与大批次卡顿

本轮依据 [issue #574](https://github.com/buxuku/SmartSub/issues/574) 的反馈、诊断包、崩溃转储和后续日志，修复具备源码证据的负载放大问题，并提供界面进程退出后的恢复入口。

## 证据与判断

- Linux 用户在 Fedora/KDE Wayland、NVIDIA 显卡环境，用 FunASR 单并发处理约 150–200 个文件；列表视图卡顿明显，曾出现界面退出而后台继续工作的情况。后续一次未白屏，但仍卡顿，说明性能问题需要独立处理。
- 三份 Linux 转储与官方 Electron 30.5.1 的二进制及调试符号匹配，均落在 `base::subtle::PlatformSharedMemoryRegion::Take()` 的 `CheckPlatformHandlePermissionsCorrespondToMode` 致命检查。可以确认直接退出机制；句柄为何异常尚未确定，不能据此认定 GPU、内存不足或 `/dev/shm` 目录权限是根因。Windows 用户的白屏也不能直接归为同一原因。
- 最新 native log 只有启动警告，缺少卡顿现场的性能数据，也没有新增崩溃证据。
- 源码存在明确的负载放大链路：读取/哈希进度频繁触发整批运行数据克隆、WorkItem 投影和广播；原有 500ms 限制仅约束检查点保存。大列表每次更新渲染全部行，实时日志也持续积累。这与用户报告的规模和操作阶段吻合，但尚不能证明其触发了 Chromium 的共享内存检查失败。

## 本轮修复

1. 在整批克隆和投影前合并进度、活动更新，每 200ms 至多发布一次。内部复用未发布的进度工作副本，对外快照和持久化状态转换继续隔离，避免外部修改和写盘失败污染状态。
2. 纯进度检查点从 500ms 改为 2s，减少主进程同步 JSON 写入及 fsync；阶段结果、暂停、取消和人工确认仍立即提交。正常退出补存待保存进度，失败则取消退出。提交阶段结果时撤销过期的进度通知。
3. 50 个及以上文件的列表只挂载可见行和少量相邻行，使用真实滚动容器和动态行高，保留稳定文件标识。
4. 日志面板限定最近 200 条，控制长任务的界面内存和渲染开销；磁盘日志保留原规则。
5. 主界面进程意外退出后弹出原生恢复提示，用户可重载当前项目并读取后台状态；不重新派发任务，也不自动循环重载。意外的 `killed` 同样提供恢复，正常退出通过退出标记和窗口状态过滤。

## 验证与范围

回归覆盖 200 文件、256 次突发进度更新合并为一次发布，快照隔离、并发进度、阶段提交覆盖待发布进度、定时检查点和退出补存。组件测试覆盖日志上限、大列表滚动到末尾及删除目标。真实 Electron 验收覆盖不同窗口宽度、动态布局、滚动、删除撤销，以及真实终止渲染进程后的项目恢复。

验收场景中，200 文件列表最多挂载 16 行。类型检查、生产构建、任务运行、组件、崩溃诊断、工作项持久化、阶段产物和缓存回归均通过。

这些改动减少主进程、IPC 和界面的工作量，并避免界面进程退出后只能停留在白屏。它们没有修复尚未定位的 Chromium 共享内存句柄异常。仍需在原 Linux 环境使用相近数量的文件完成转写回归；如果继续卡顿，需要采集卡顿发生时的主进程/渲染进程性能记录，后续判断同步存储、界面或模型资源争用的占比。
