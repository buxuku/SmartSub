## Context

[#562](https://github.com/buxuku/SmartSub/pull/562)（变更 `fix-qwen-asr-long-segments`，下称「前一个变更」）把 Qwen3-ASR 的「最长语音」收敛到默认 15 秒、上限 20 秒，并在转写后对放不进解码预算的段记 warning。它只能降低概率，原因在前一个变更 design 的「VAD 的『最长语音』只是软限制，过冲呈长尾」一节：sherpa VAD 超过上限后只是把最短静音降到 0.1 秒、阈值升到 0.90，从不硬切；本机探针里完全没有停顿的素材在任何上限下都只有一整段，上限取 15 秒时仍有约两成音频落在超过 28 秒的段里。前一个变更因此把 worker 级硬切分列为首要后续项（该变更 tasks 8.2）。

解码预算的算式沿用前一个变更：`15 + ceil(13 × 秒数) + max_new_tokens ≤ max_total_len`，默认 512 / 128 下约 28 秒放得进，超过约 38 秒音频本身被丢掉。sherpa-onnx 维护者在 [#549](https://github.com/buxuku/SmartSub/issues/549) 里的建议是把段切到 20 秒以内，并说明输入越长内存越多。

现状（读自 `extraResources/sherpa/worker/sherpa-worker.js`）：

- `transcribe()` 里的 `drain()` 对 VAD 吐出的每个段做 `createStream()`、`acceptWaveform(seg.samples)`、`decodeAsync()`，段多长就整段送进去。结果里带文本的 `segments`（cue）与每个解码单元的 `vadSegments`（起止秒数）随 `done` 消息回报
- 每个 VAD 段新建一个 stream，段与段之间没有上下文，所以切开不会丢掉原有的上下文
- 现有代码在 `vad.pop()` 之后仍然使用 `seg.samples`，所以可以直接对它切片
- worker 不经 webpack，是纯 JS，用 `require(path.join(__dirname, 'wav-io.js'))` 加载同目录模块。`electron-builder.yml` 在 mac、win、linux 三处都把 `./extraResources/sherpa/` 以 `**/*` 整目录打包
- 下游对 `vadSegments` 的用法是漏听检测（`missedSpeechWarning.ts`）、时间贴齐，以及前一个变更的告警。漏听检测先用 `mergeSpeechIntervals` 把首尾相接的区间并起来，所以只关心「有语音的区间」的并集

### 切点探针（本机，不入库）

方法：Node 脚本，20 ms 一帧算 RMS，三帧能量平滑。素材沿用前一个变更的探针：55 段约 2 分钟的合成语音（11 个 macOS `say` 语音，停顿被 `silenceremove` 压成 60 / 80 / 90 / 100 / 120 ms 的残余停顿），另有中英文各一段完全没有停顿的（145 秒、123 秒）。把每个文件当成「VAD 没切开的一整段」，上限 L = 20 秒，按 n = ceil(d / (L − 2r)) 等分，在每个理想切点前后 r 秒内取能量最低的帧；对照组是不搜索、直接切在等分位置的切点。

指标有两个：切点所在帧的 RMS 是否 ≤ −45 dBFS（这是造素材用的 `silenceremove` 门限，即落在停顿里），以及切点能量相对整段中位数的差（dB，取中位数）。

| 素材           | r    | 切点数 | 切在停顿里：搜索 / 等距 | 相对中位数的能量（dB）：搜索 / 等距 | 片长（秒） |
| -------------- | ---- | ------ | ----------------------- | ----------------------------------- | ---------- |
| 55 段残余停顿  | 1 秒 | 373    | 93% / 2%                | −69.8 / −0.2                        | 14.0–19.1  |
| 55 段残余停顿  | 2 秒 | 417    | 98% / 6%                | −71.3 / 0.5                         | 10.9–18.5  |
| 55 段残余停顿  | 3 秒 | 484    | 100% / 2%               | −71.5 / 0.2                         | 7.3–18.5   |
| 2 段完全无停顿 | 1 秒 | 14     | 14% / 0%                | −27.0 / 0.2                         | 14.9–19.0  |
| 2 段完全无停顿 | 2 秒 | 16     | 31% / 0%                | −28.0 / −2.3                        | 12.8–16.6  |
| 2 段完全无停顿 | 3 秒 | 18     | 50% / 0%                | −28.9 / 0.6                         | 8.1–18.1   |

结论：

- 有残余停顿时，搜索把切点从说话中间挪进了停顿：93–100% 落在停顿里，等距切点只有 2–6%
- 完全没有停顿时，切点仍比整段中位数低约 28 dB，但落在真正停顿里的只有 14–50%，其余是语音里最安静的帧。这种素材里切点仍可能落在词中，这是硬切分的固有限度，不是实现问题
- r = 2 秒是折中：片长 10.9–18.5 秒。r = 3 秒片数更多、更碎，收益主要在无停顿素材（落在停顿里的比例 31% → 50%）
- 每片都不超过 20 秒（最长 19.1 秒），与构造上的保证一致
- 局限：这是合成语音。−45 dBFS 正是造素材时的门限，真实录音的底噪高于数字静音，所以应主要看「相对中位数的 dB 差」。也没有词边界标注，无法统计切在词中的比例，更没有 Qwen3-ASR 模型可以量化识别质量（tasks 7.1、7.2）

## Goals / Non-Goals

**Goals**

- 默认设置下，送进 Qwen3-ASR 解码的每个单元都不超过 20 秒、且放得进预算；不丢任何音频
- 没有停顿的素材（#549 的复现类型）不再整段静默失败
- 被切开的情况在日志里可见
- 参数缺省时，worker 对所有引擎的行为与现在一致；整个功能可以靠去掉一个参数关掉

**Non-Goals**

- 保证切点不落在词中：没有停顿的音频做不到，只能选最安静的位置
- 重叠窗口、文本去重合并（见 D2 的替代方案）
- 界面开关或上限、给其他引擎启用、升级 sherpa-onnx、改动前一个变更的钳制与默认值
- 让切分提示进入任务界面

## Decisions

### D1: 在 worker 里、VAD 出段之后切

只有 worker 手里有完整的 VAD 段样本。TS 侧拿到的只是 `{start, end}`，要切就得重新读音频、再发多次转写请求；放在 worker 里，切片直接是 `seg.samples.subarray`，不增加一次音频读取，也不增加主进程与 worker 之间的往返。

切分发生在 VAD 之后，不影响 VAD 实例与识别器实例的复用：新参数不进 `buildKey` 与 `buildVadKey`。

替代方案：

- **在 TS 侧切**：要重读音频，拆成多次请求，进度与取消要在主进程里重做
- **转写前先把音频文件拆开**：改动面大，还会破坏 VAD 对全文件的连续处理

### D2: 等分，每个切点取附近能量最低的帧

算法（纯函数，输入样本、采样率、上限 L，输出各片的起止样本）：

1. d = 样本数 / 采样率。d ≤ L 时只返回一片，即原段
2. r = min(2 秒, L / 4)，n = ceil(d / (L − 2r))。每片理想长度 d / n ≤ L − 2r
3. 以 20 ms 为一帧算能量，再做三帧平滑
4. 第 k 个理想切点是 k·d/n（k = 1 … n − 1）。在它前后 r 秒内（不越出该段）取平滑能量最低的帧，以该帧中心为切点；能量并列时取离理想位置最近的，所以全零或平坦信号退化成等分
5. 各片首尾相接，合起来恰好覆盖原段

每片长度的上界：理想长度加上两端各移动 r，即 d / n + 2r ≤ L，所以不超过上限是构造出来的，不靠事后检查。n 取等分而不是「贪心切满再留尾巴」，是为了避免最后一片极短。

替代方案：

- **等距硬切**：最简单，成本几乎一样，但切点随机。探针里等距切点只有 2–6% 落在停顿里，选最安静处是 93–100%
- **重叠窗口加文本去重合并**：切在词中间的损伤最小，但 Qwen3-ASR 没有词级时间戳，跨语言、跨标点的去重容易重复或丢字，风险最高
- **对长段重跑更严的 VAD**：VAD 超过上限后本来就已经降到最严的参数（阈值 0.90、最短静音 0.1 秒），探针里没有停顿的素材仍然不切，重跑不会有新切点
- **用 Silero 的语音概率找切点**：要把模型再对长段推理一遍，参数和失败面都更多；能量最低点在探针里已经足够好，留作后续

### D3: 上限 = min(20 秒, 预算能容纳的秒数)，且不低于 1 秒

`segment_hard_max_s = max(1, min(20, fitSeconds))`，其中 `fitSeconds = floor10(max(0, (max_total_len − 15 − max_new_tokens) / 13))`，与前一个变更的 `findQwenOverBudgetSegments` 是同一个口径（floor10 是向下取整到 0.1 秒）。默认预算下是 20 秒；有人把预算调小，上限随之收紧，保证每片放得进；预算放不下 1 秒音频的离谱配置取 1 秒，由前一个变更的告警兜底。

20 秒与前一个变更的 VAD 硬上限一致，也是 sherpa-onnx 维护者的建议。它和 VAD 软限制的默认 15 秒不矛盾：15 秒是让 VAD 尽量自己在停顿处切开（不伤词），20 秒是兜底。

取舍：超过 20 秒的段一律切开，包括 20–28 秒、原本放得进预算的那部分。代价是这些段多了切点；好处是单一参数、规则好懂，并满足维护者「不要超过 20 秒」的建议。前一个变更的探针里，VAD 上限取 20 秒的那一行：687 段中有 129 段超过 20 秒，其中 45 段超过 28 秒，也就是约 84 段属于这种「放得进却被切开」的段（默认的 VAD 上限是 15 秒，具体数字会不同，量级可参考）。

替代方案：触发线取预算线（28 秒），片长仍不超过 20 秒。能少切约 84 段，代价是两个参数、段最长可以到 28 秒（内存与维护者的建议）。见 Open Questions。

### D4: 每片独立 cue，`vadSegments` 报告实际解码的片，另报 `splits`

- 每片一个 stream、一次 `decodeAsync`，有文本的片各出一个 cue，起止是该片在整段音频里的绝对秒数，片与片首尾相接、不重叠
- `vadSegments` 列出实际送去解码的片（没被切的段原样）。下游先把首尾相接的区间并起来，并集不变，漏听检测与时间贴齐不受影响；而前一个变更的告警按「实际解码的单元」计算才是对的
- `done` 消息新增 `splits`：每个被切开的原 VAD 段一项，`{ start, end, pieces }`，没有被切时是空数组。引擎据此记日志
- 片之间检查取消；进度的已处理秒数随片递增；活动事件里每一片是一个解码单元

替代方案：`vadSegments` 仍报原 VAD 段，另加 `decodeSegments` 报片。多一个字段，而下游本来就不区分，告警却要改成读新字段。

### D5: 只给 Qwen3-ASR 启用

参数由 `buildQwenParams` 给出，其他三个引擎的请求不带，worker 里「缺省即关闭」。机制是通用的，FireRedASR 以后要用，传同一个参数即可。这次不碰它们：FireRedASR 有自己的段长闸（默认 30 秒、上限 60 秒），它的模型上限我没有核实；FunASR 与 Parakeet 没有同类预算限制。

### D6: 前一个变更的告警保留，对象改为实际解码的片

告警逻辑与文案不改，只是输入的 `vadSegments` 现在是片。默认预算下，切分生效后每片 ≤ 20 秒，不会再触发；它只在 worker 没切（参数缺失、旧 worker）或预算被调小到放不下时触发，作为兜底。

被切开时引擎另记一条 info：`qwen(sherpa): split N VAD segment(s) longer than Xs into M pieces at the quietest points (longest A s-B s); when the audio has no pause a cut can land inside a word.`，让「为什么这里多了一个字幕边界」在日志里有迹可循。

### D7: 切分逻辑只在 worker 里实现一份

逻辑放在 `extraResources/sherpa/worker/segment-split.js`，与 `wav-io.js` 并列，TS 侧只传 `segment_hard_max_s`。没有 TS 副本，也就没有 `sherpaConfig.ts` 那种「worker 内联一份、TS 一份」的双份维护。前一个变更 tasks 8.2 里「要与 `sherpaConfig.ts` 双份维护」的担心，在这个方案里不成立。

测试：纯函数用 `scripts/test-segment-split.cjs` 直接 `require`，并入 `yarn test:engines`；`scripts/test-sherpa-worker.cjs` 用 `vm` 加载 worker，它的 `require` 桩现在只认 `path` 与 `wav-io.js`，要补一条把 `segment-split.js` 映射到真实实现。其他脚本（`windows-nonascii` 系列等）用 `worker_threads` 跑真实 worker，同目录的 `require` 自然解析得到。

## Risks / Trade-offs

- [没有停顿的素材里，切点仍可能落在词中，识别质量未知] → 选最安静的位置，日志里记 info，文档如实写；请 issue 作者复测（tasks 7.1）；不把它写成「彻底解决」
- [本机没有 Qwen3-ASR 模型，被切开的音频的识别质量无法端到端验证] → 切分函数用合成信号测，worker 层用桩测，引擎层测参数与日志
- [探针是合成语音，−45 dBFS 是造素材时的门限] → 主要看相对整段中位数的 dB 差；真实素材上的表现列入 tasks 7.2
- [原本放得进预算的 20–28 秒段也被切开，多了切点] → D3 的取舍，Open Questions 里留了备选
- [每片独立解码，片间没有上下文] → Qwen 本来就是每个 VAD 段新建 stream，行为一致
- [worker 与 TS 之间多了一个参数和一个返回字段，可能漂移] → 类型加上，引擎层测试覆盖
- [新文件没被打包，或 worker 在包里找不到它] → 打包规则是整目录 `**/*`，tasks 6.7 逐条核对；`worker_threads` 路径的脚本（含 Windows CI 的 sherpa 检查）会 `require` 真实文件
- [切分增加解码调用数] → 总音频时长不变，计算量基本不变；Qwen 每次解码本来就重建并清零 KV cache

## Migration Plan

无设置迁移，已保存的设置不变。参数缺省时 worker 行为与现在一致。回退：去掉 `buildQwenParams` 里的 `segment_hard_max_s`，功能即关闭，worker 里的代码保持不触发。

## Open Questions

- 触发线与片长上限要不要分开（D3 的替代方案）？默认建议保持单一参数 20 秒；若真实素材显示 20–28 秒的段本来识别得很好，再改成两个参数
- FireRedASR 要不要同样启用？需要先核实它的模型长度上限，再看它自己的段长闸（默认 30 秒、上限 60 秒）够不够
- 是否在界面暴露开关或上限？目前没有需求，且前一个变更已经说明 `qwenMaxTotalLen` / `qwenMaxNewTokens` 没有界面入口
- 切分提示是否进入任务界面？需要新的任务警告通道，与前一个变更的 tasks 8.3 合并考虑
