## Context

任务页上的表单属于一个工程草稿（`useTaskProjectPersistence` 以 150 ms 防抖存进 `taskDraft`）。新任务的初值来自「默认配置」——`electron-store` 里的 `userConfig`：`getUserConfig` 读出时叠加 `defaultUserConfig` 与惰性推断的 `subtitleOutcome`，渲染进程再用 `newTaskDefaults(preferences, taskType)` 套上任务类型。这份默认配置的语义是「上次用什么，下次默认什么」。

往里写的历史：

- **3.8：** `useFormConfig` 在每次表单变化时把整份配置写进 `userConfig`。体验是对的，但整份覆盖有副作用：打开一个旧工程、只改一项，旧工程里所有陈旧的值都会冲掉默认配置。
- **3.9：** 任务页改成工程草稿，去掉了这条写入。调整过的参数不再进入默认值。
- **3.10：** `rememberTaskDefaults`——任务被主进程确认之后，把该任务的配置整份记为默认值。只调整、不运行的参数仍然不保存。

`electron-store` 在首次启动时就把 `defaults.userConfig`（出厂默认）整份写入存储文件，所以真实存储里本来就有全部出厂默认键；之后新增的默认键、缺失的键由 `getUserConfig` 读取时叠加。因此「删掉存储里的某个键」的效果是「出厂默认重新生效」。

## Goals / Non-Goals

**Goals:**

- 用户在任务页调整的参数很快（防抖后）成为新任务的默认值，不必运行任务（3.8 的体验）。
- 不重蹈 3.9 去掉写入时的顾虑：打开或恢复旧工程不写默认值；代码做的自动纠正不被当成用户的选择。
- 刚改完就离开页面、关闭窗口或新建任务，最后一次改动也不丢。
- 写入失败不打断编辑，也不丢改动。

**Non-Goals:**

- 新建任务向导实时写入（用户已确认范围仅任务页；向导继续只读取默认值，`pipeline-task-wizard` 规格不变）。
- 迁移已保存的值、场景预设标签的检测规则、多窗口之间的广播。
- 版本号与 `Changelog/`（发版时写）、新增界面文案。

## Decisions

**1. 补丁，不是整份覆盖。**
渲染进程只发送用户改过的键，主进程把补丁合并进已存配置（`applyTaskDefaultsPatch`），没出现在补丁里的键一概不动。这是与 3.8 唯一有意的差别：旧工程里的陈旧值、读取失败后的空表单都不可能冲掉默认配置；单纯「开始任务」没有改动，也就不产生写入。
备选：还原 3.8 的整份覆盖——否决，正是它让 3.9 把写入整个去掉。备选：保留 3.10 的「开始任务时记忆」——否决，这是用户明确要改的行为。

**2. 会话基线 + 差分，基线只在主进程确认保存之后前进。**
每次装载表单（`hydrateSnapshot`：新任务、恢复工程、切换工程）开一个会话，基线是装载时表单里的值。`edit(values)` 防抖后按顶层键对基线做 `isEqual` 差分，只发送不同的键，值先拷贝，之后表单在原地改动也不会改变已经算好的补丁。改回基线值就没有差分，什么也不发送；装载本身不是编辑，零写入。
表单里被移除或置为 `undefined` 的键，补丁里写 `undefined`，主进程据此删键（结构化克隆经 IPC 保留 `undefined`）。预设把某些参数置为未设置时，就是这样回到出厂默认。
基线只在 `send` 成功之后才前进：失败的键留在差分里，下一次保存自然带上。

**3. 自动纠正不记忆：`correctValue` 只移动基线。**
任务页有几处「代码改表单」：翻译服务商回落到可用的默认值（清理 `-1` 或已被删除的服务商 id）、转写引擎 / 模型 / `asrProviderId` 在已选项不可用时回填、`sourceSrtSaveOption` 的 `noSave → fileName`（仅生成字幕页）。它们是页面为自己兜底，不是用户的选择；如果被记住，「仅生成字幕」页会把 `fileName` 写进翻译任务的默认值，模型暂时不可用时的回落也会把用户偏好的引擎 / 模型换成临时的替代项。`correctValue(name, value)` 先把基线里的该键改成新值（`form.watch` 在 `setValue` 里是同步触发的，所以基线必须先于 `setValue`），再改表单，差分里就没有这一项；之后用户亲手改同一个键，仍然照常被记忆。
用户点「采用建议服务商」的 `setValue` 是用户操作，保持原样。
备选：在发送处按键名排除纠正过的字段——否决：每个纠正点都得登记，而且之后用户的真实选择会被一并排除。

**4. 逐任务字段用黑名单，不用白名单。**
`taskType`、`dub`、`compose`、`gates`、`cloudUploadConsent`、`manuscriptPath`、`manuscriptName` 属于单个任务（`PER_TASK_KEYS`）：类型由所进入的页面决定，配音 / 合成 / 把关是向导里逐任务配置的，云上传同意不能悄悄继承，参考文稿是任务输入。其余的键都记忆，不设白名单：以后新增的设置不用登记就会被记住，与 3.8 一致。渲染进程在差分时按 `isTaskDefaultsKey` 过滤，主进程合并时再过滤一次（纵深防御；同时拦下 `__proto__`，并剔除存储里残留的参考文稿键）。
备选：白名单——否决：每加一项设置就要记得登记，漏登记等于又一个「调了不记忆」的 bug。

**5. 防抖 400 ms，发送串行，空闲时同步发出。**
`createTaskDefaultsSync` 复用 `createDebouncedPersist`（`flush` 同步提交），400 ms 与其它防抖保存的设置编辑器一致。发送串行：忙时排在上一次之后，每次发送在轮到它时才对「上一次保存产生的基线」做差分，所以「改了又改回」而前一次还在途中，最终值也是对的。空闲时 `run` 同步启动，请求在调用方返回前就发出：页面卸载时的冲刷先于下一页的 `getUserConfig`。
模块顶层不访问 `window`（`scripts/test-unified-task-draft.ts` 用 `tsx` 导入 hook 模块），`send` 由 hook 注入，所以同步逻辑不依赖 React 与 Electron，可以直接用 jest 假定时器测试。

**6. 冲刷点。**

- 装载另一个工程（`sync.start`）：旧会话还在防抖中的改动先写入，再建新基线；待写入的改动带着自己的会话，结果不会污染新会话的基线。
- hook 卸载与 `beforeunload`（窗口关闭或刷新，尽力而为）。
- 任务页为新任务读取默认值之前（`await flushDefaults()`）：刚改完马上新建任务，新任务拿得到最新值。

**7. 失败语义：不打断，在下一个机会重试。**
主进程写入失败时向调用方抛错（`ipcMain.handle` 不吞），渲染进程的 `updateTaskDefaults` 在 `result.success !== true` 时同样抛错。同步模块只记日志（`onError`），不弹提示、不打断编辑——工程草稿的保存失败本来就有显式提示（「任务草稿保存失败」），默认配置只是「下次的初值」。基线不前进，所以下一次修改会带上没写成的键。
用户改完就离开的情形：会话记下最近一次编辑（`latest`）和上次保存是否失败（`failed`），`flush` 与 `start` 在没有待写入的编辑时重试失败的会话。重试发出时乐观地清掉 `failed`，避免紧接着的另一次冲刷再排一个重复的重试；重试再失败就再标记。
备选：弹错误提示——否决：存储暂时不可写时每次调整都会打扰用户，而它在下次保存时多半就恢复了。

**8. 只在任务页打开，固定快照页只读。**
`syncDefaults` 选项默认 `false`，向导（`TaskWizard`）不受影响，继续只读取默认值。任务页传 `syncDefaults: !configSnapshot`：展示固定快照的页面是只读的，不记。该选项在编辑发生时经 ref 读取，所以页面在可编辑与只读之间切换（打开另一个工程）时立即生效。

**9. 删除「开始任务时记忆」，只留一套机制。**
`TaskControls` 的 `rememberDefaults` 属性与 `rememberConfig`、共享规则里的 `toRememberedTaskDefaults`、hook 里的 `rememberTaskDefaults`、IPC 的 `rememberTaskDefaults` 全部删除：编辑时已经记住了，启动时再整份写一遍只会带来第二套语义，并且重新引入「整份覆盖」。`rememberSelection`（写 `lastUsedTranscription`，供转写引擎 / 模型的回填）不动。

**10. 与 `fix-translate-content-defaults` 的关系。**
那个变更把「3.9.x / 3.10.x 期间已保存 `sourceAndTranslate` 的用户，改一次就会被记住」写成已知限制的出路。在 3.10 里这要等到任务运行之后才成立；有了实时记忆，用户在配置栏改一下输出内容，下一个新任务就是新的选择。

## Risks / Trade-offs

- [每次保存都重写整个存储文件] → `electron-store` 的每次 `set` 都是同步重写整个 `config.json`。3.8 是每次表单变化写一次；现在先防抖 400 ms，再对基线差分，没有变化就不发送，写入次数比 3.8 少得多，只发生在用户停顿时。
- [写入失败静默] → 只记日志，在下一次修改或离开页面时重试；存储一直不可写时默认值保持旧值，而工程草稿的保存失败本来就会提示。`task-project-persistence` 端到端用真实的目录权限锁定验证过：写入失败不打断编辑，已保存的默认值不变，离开页面后补写成功。
- [用户试探性的调整也会被记住] → 这就是「上次用什么，下次默认什么」，与 3.8 一致；改回去同样被记住。打开旧工程只改一项，被记住的只是这一项。
- [`beforeunload` 里的冲刷是尽力而为] → 请求在页面卸载前同步发出，主进程按到达顺序处理；极端情况下（进程被强杀）仍会丢失最后 400 ms 内的改动。
- [多窗口] → 不做广播；后保存的补丁只覆盖它自己改过的键，不会整份覆盖另一个窗口刚写的值。
- [场景预设标签] → 新任务继承记住的预设后，标签可能显示「专家自定义」：预设会把 `maxSubtitleChars`、`speakerDiarizationCount` 等置为未设置，经「删键」后由出厂默认补回 `0`，而 `detectCurrentPreset` 把这个 `0` 当成用户改过的值。出厂默认的新任务本来就是同样的结果（改动前一样），参数值也被正确继承，所以本次不改检测规则；若要修，应单独处理 `detectCurrentPreset` 对出厂 `0` 的判定。
