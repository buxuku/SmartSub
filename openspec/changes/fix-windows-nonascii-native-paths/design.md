## Context

原生库（sherpa-onnx、whisper.cpp 的音频解码）用窄字符 API 打开文件，Windows 系统代码页不是 UTF-8 时，含非 ASCII 字符的路径对它们等于「不存在的文件」。中文用户名让默认安装目录、`userData`、`%TEMP%` 都成了这种路径，所以问题不是个别文件，而是整套默认值一起失效。

更麻烦的是失败的**形态**不统一，用户看到的往往不是「打不开文件」：

| 形态               | 例子                                                            | 后果                                |
| ------------------ | --------------------------------------------------------------- | ----------------------------------- |
| 静默失败           | Silero VAD 构造返回空句柄、whisper addon 读不到音频仍 resolve   | 0 个语音段 / 0 条字幕，请求「成功」 |
| 抛错但没有原因     | 降噪等构造函数只抛 `Please check your config!`，原因只写 stderr | 用户看到的错误没法行动              |
| 返回失败值，没人看 | `writeWave` 返回 `false`，原来没有调用方检查                    | 产物悄悄缺失，下游读到不存在的文件  |

约束：

- 原生库是预编译的上游产物，不改它；也不能要求用户改系统设置（例如开启 Windows 的「Beta：使用 Unicode UTF-8 提供全球语言支持」）
- ASCII 用户、macOS、Linux 的行为必须完全不变
- 每个兜底在自己失败时都回退为原路径，不会比不处理更差
- 要能在真实 Windows 上验证：开发机是 macOS，只靠本机测试证明不了「Windows 上打不开」这件事

## Goals / Non-Goals

**Goals**

- 中文用户名、默认安装 / 数据 / 临时目录下，VAD、降噪、本地 ASR、声音克隆分析、内置 whisper 转写开箱即用
- 失败不再静默：错误带着原生给出的原因；涉及非 ASCII 路径时给出可操作的建议
- 诊断包能一眼看出路径是否会出问题，不用再向用户要路径
- 用 CI 在真实 Windows 上守住这件事，回归能被发现

**Non-Goals**

- 搬运或复制 GB 级用户模型（说话人分离、TTS 的模型）：只提示
- 覆盖尚未验证的路径：faster-whisper（Python / CTranslate2）、ffmpeg 字幕烧录（libass）
- 探测或适配具体代码页：判据取保守的「路径含非 ASCII」，不去判断当前代码页是不是 UTF-8
- 改变 `unified-storage-root` 的中文路径校验

## Decisions

### D1: 判据是「win32 且路径含非 ASCII」，不是「含中文」

`hasNonAscii`（任何 `> 0x7F` 的字符）+ `process.platform === 'win32'`。窄字符 API 按代码页解码，不只中文：带音标的拉丁字母、emoji 在非 UTF-8 代码页下同样会出错。`unified-storage-root` 的 `containsCjk` 刻意不拦西文变音符（那是「禁止用户选」的硬校验，误伤的代价高），而这里只是「要不要走兜底」，宁可多走。

用户开启了 Windows 的 UTF-8 系统代码页时，原生本来就能打开，兜底是多余的，但无害：JS 读写与原生逐字节 / 逐样本一致（CI 对拍），暂存副本与源文件逐字节相同，代价只是一次复制或解码。所以不探测代码页。

替代方案：

- **按 CJK 判断**：漏掉变音符用户名，且这些用户在非 UTF-8 代码页下同样失败
- **探测代码页（`GetACP`）后再决定**：需要原生调用或额外进程，探测本身就是新的出错点，而兜底的代价很小

### D2: 按文件的性质选对策，不一刀切

| 文件                                 | 特点                      | 对策                                            |
| ------------------------------------ | ------------------------- | ----------------------------------------------- |
| 随包 VAD / 降噪模型                  | 公共、不可变、共约 2.3 MB | 复制到 ASCII 目录（内容寻址）                   |
| 用户音频（抽出的 wav、声音克隆素材） | 私有、可能很大            | 不复制：worker 内 JS 读写 / whisper 走 PCM 缓冲 |
| GB 级用户模型（说话人分离、TTS）     | 体积大、用户可选位置      | 不搬，失败时提示换到纯英文统一存储目录          |

用户音频不复制到任何共享目录：暂存目录对所有用户可见，把私人素材放进去既有隐私问题，也会留下垃圾。GB 级模型复制会成倍占用磁盘，且用户本来就能通过统一存储目录自己选位置，提示比自动搬运更合适。

### D3: 暂存副本，而不是联接点、短路径名或 UTF-8 清单

未采纳的做法（**这些没有实测过**，是设计层面的取舍，不是「试了不行」）：

- **NTFS 联接点**：给含中文的目录建一个 ASCII 名字的联接点。递归删除类工具（清理软件、手动删除、卸载程序）可能跟进联接，误删目标目录里的内容；部分终端安全产品（EDR）对联接点敏感；另外还要找一个可写的 ASCII 位置来建，清理时机不明确。复制 2.3 MB 的公开模型没有这些风险，也更好测试
- **8.3 短路径名**：8.3 短名在较新的 Windows 上可以按卷关闭，不能依赖它一定存在
- **进程级 UTF-8 代码页（`activeCodePage` 清单）**：要改 Electron 可执行文件的清单，是全局行为变更，影响该进程里**所有**窄字符调用（包括 Chromium 与其他库），风险面远大于要解决的问题；只对 Windows 10 1903 及以上有效，本机也无法验证

### D4: 暂存目录候选与内容寻址

候选顺序：`<userData>/native-models` → `%ProgramData%\SmartSub\native-models` → `%PUBLIC%\SmartSub\native-models` → `%SystemDrive%\SmartSub\native-models`，自身含非 ASCII 的候选直接剔除（暂存到另一个中文目录没有意义）。用户名是英文时第一个候选就可用；中文用户名时 `userData` 被剔除，落在 `ProgramData`（标准用户可以在其中新建目录）。

目标路径是 `<base>/<sha1 前 16 位>/<ASCII 文件名>`，复用前逐字节比对：

- 同一个模型多次启动只写一次；模型升级后内容变了，落在新目录，旧副本不会被误用
- 另一个 Windows 用户先写入的目录对本用户只读时，只要内容一致仍可复用，写不了再换下一个候选
- 先写临时文件再改名，另一个进程不会读到写了一半的模型；目标被并发写好时校验通过即采用
- 超过 64 MiB 的文件不暂存（这个机制只面向随包小模型），返回原路径并记 warning

代价：旧副本不清理（每个模型版本约 2.3 MB，模型更新才会新增）。

### D5: worker 里的 wav 读写用 JS 实现，口径与原生一致

`wav-io.js` 放在 `extraResources/sherpa/worker/`，纯 JS、不经 webpack，被 sherpa / tts / speaker-diarization 三个 worker 共用。含非 ASCII 的路径才走 JS（`SMARTSUB_FORCE_JS_WAV=1` 可在任何平台强制，测试与排查用），其余仍走原生，ASCII 用户的行为与产物不变。

编解码与 sherpa-onnx 的 `wave-reader.cc` / `wave-writer.cc` 对齐：读取第一声道、8 位无符号 / 16 位 / 32 位整数 / 32 位浮点归一化到 [-1, 1)；写入单声道 16 位 PCM，按「float × 32767，向零截断，夹到 int16」量化。本机用原生库对拍：写出的文件与原生逐字节相同，读到的样本与原生完全一致；Windows 上由 CI 再对拍一次（含中文目录）。

有意的差异：

- 读取额外接受 `WAVE_FORMAT_EXTENSIBLE`（子格式为 PCM / 浮点）。ffmpeg 输出 32 位或多声道 wav 时会写这种头，原生读取器会拒绝，JS 能读
- 32 位整数按 2^31 正常归一化；原生实现里除数的写法带符号怪癖，不复刻。应用自己产出的 wav 是 `pcm_s16le`，不受影响
- `writeWave` 失败是异常，不再返回 `false`

### D6: 内置 whisper 的非 ASCII 音频路径改用 PCM 缓冲

whisper.cpp addon 支持用 `pcmf32`（`Float32Array`）代替文件路径；此时 `fname_inp` 仍必须是字符串，置 `''`。非 ASCII 路径由 JS 解码 16 kHz 16 位 PCM wav（应用自己产出的格式），以缓冲交给 addon；addon 对缓冲输入不写任何输出文件，其余行为（VAD、token 时间轴、进度、取消）与文件输入一致。解不了（不是 16 kHz 16 位 PCM、文件读不了、没有样本）时原样透传并记 warning，行为不会比之前更差。

接入点放在 `addonLoader.ts` 的 `whisperAsync` 上（`withNativeSafeAudioInput`），而不是某个引擎里，这样内置转写（单次与分块）和声音克隆的参考音频转写自动覆盖，以后新增调用方也不会漏。

内存：addon 会把缓冲拷贝数份，1 小时 16 kHz 单声道一份约 230 MB。所以这条兜底路径的分块计划从默认的「超过 4 小时才分、每片约 1 小时」收紧为「超过 1 小时才分、每片不超过 30 分钟」（`PCM_INPUT_CHUNK_PLAN`），`prepareBuiltinChunks` 因此多接受一个可选的计划参数；ASCII 路径仍用默认计划。

### D7: 静默失败靠 stderr 监视转成错误

`vad is nullptr` 只出现在 worker 的 stderr，请求本身以 0 个语音段「成功」结束，所以必须把两者关联起来：

1. `UtilityHost` 增加可选 `onStderrLine`，按行回调（处理半行与流结束时的残行）
2. `SherpaFunasrRuntime` 为**每个 worker** 建一个 `NativeStderrWatch`：统计 `vad is nullptr`，并在第一次出现时保存其之前的原因行（只留最具体的 2 行，之后几百行重复只计数）。每个请求记下发出时的计数
3. transcribe / detectSpeech 以零个分段结束时，等 200 ms 再判断（stderr 管道与 IPC 消息是两条独立通道，到达先后没有保证）；这期间新增了 `vad is nullptr` 就改为 reject，错误里带原生原因，涉及非 ASCII 路径时追加建议
4. 同时释放持有空 VAD 的 worker，下一次请求在新 worker 上重试；仅当它仍是当前 worker 时才释放，避免误杀已经重建的 worker

为什么是「零结果 + 期间出现过 `vad is nullptr`」：真正的静音文件也会得到零个语音段，不能把所有零结果都当错误；而只看 stderr 又会把别的请求的噪声算到这一个头上。两个条件同时成立才报错。

识别器 / 降噪 / TTS / 说话人分离的构造错误本来就抛异常，只是消息只有 `Please check your config!`：对这类「打不开文件」特征的消息，在 Windows 且请求里确有非 ASCII 路径时追加中英文建议（取消、忙碌等其他错误原样返回）。声音克隆在 VAD 失败回退能量法时补一条 warning，原来这里是静默吞掉。

### D8: 诊断包只导标志，不导路径

`appInfo()` 增加 `userDataPath` / `installPath` / `tempPath`，每项只有 `{ nonAscii, hasSpace }`，复用已有的 `describePathSetting`。路径本身含用户名，不属于诊断包可以带的内容；标志已经足够判断是否撞上这类问题。

### D9: 在真实 Windows 上先复现，再断言

本机是 macOS，无法验证「Windows 上打不开」。所以先加只报告、不断言的探针 workflow，用运行结果确认根因（`[BUG REPRODUCED]` 对应 `[control ok]`），再写修复；修复之后探针保留为信息性步骤，旁边加断言步骤。这样每次运行都能看出这台 runner 上缺陷是否还在，断言才有意义（如果缺陷在某天的 runner 上不复现，通过的断言就不能证明对策有效）。

CI 在 `windows-latest` 上，ANSI 代码页是 1252，不是中文系统的 936。两者同属「窄字符 API 按非 UTF-8 代码页解码」，失败机制相同，但 936 没有直接验证，脚本会把实际 ACP 打印出来。

## Risks / Trade-offs

- **代码页 936 未直接验证**：CI 是 1252，同类但不同；真实中文机器需要手测（见 tasks 5.1）
- **依赖上游日志文案**：D7 依赖 `vad is nullptr` 这一行。上游改了文案，这一条会退回到「静默零结果」，但不会误报；构造抛错、`writeWave` 异常、whisper PCM 输入这几条不依赖文案
- **200 ms 宽限**：只影响「零结果」的请求，正常请求不受影响；真正的静音文件多等 200 ms 才返回
- **暂存副本不清理**：每个模型版本 ≈ 2.3 MB，换模型才会新增；换来的是不需要清理时机的判断
- **PCM 兜底的内存**：1 小时音频一份约 230 MB，addon 内部会拷贝数份；收紧分块阈值缓解，但极端长音频的内存峰值没有实测（见 tasks 5.2）
- **Windows UTF-8 代码页用户**：兜底多余但无害（D1）
- **未覆盖的路径**：faster-whisper（Python / CTranslate2）和字幕烧录（libass）可能有同类问题，没有验证，也没有改动
