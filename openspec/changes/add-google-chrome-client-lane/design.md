# Design: add-google-chrome-client-lane

## Context

**翻译契约。** `handleAPIBatchTranslation`（`main/translate/services/api.ts`）以 `batch.map((s) => s.content.join('\n'))` 调用 `translator(string[], provider, from, to, { signal, glossaryEntries })`，要求返回等长数组，条数不等即抛错；失败按 `maxRetries` 重试，用尽后该批保留原文并标记 `failed`，任务继续。条目内部的多行文本以 `\n` 留在同一个字符串里，翻译函数必须自己处理。

**错误分类。** `isConfigurationError`（`main/translate/utils/error.ts`）把含 `401`、`403`、`forbidden`、`unauthorized`、`access denied`、`authentication failed` 的消息当成配置错误并中止整个任务，但消息里含 `network` 或 `timeout` 时除外；含 `not supported language` 的一律是配置错误。所以谷歌通道的运行期错误必须带 `(network)`，`not supported language` 只能用于「请求前的语言映射失败」。

**`googleFree` 现状。** `main/service/googleFree.ts`（91 行）逐条 `GET translate.googleapis.com/translate_a/single?client=gtx&sl&tl&dt=t&q=`，单条截断到 5,000 字符，空白条目不发请求；每个请求前 `acquire('googleFree:<providerId>', resolveRateLimitConfig(proof), signal)`；超时取全局 60 s（`TRANSLATION_REQUEST_TIMEOUT`）；错误统一写成 `Google free translate failed (network): …`。它没有任何失败记忆：被限的网络里每一条都会再撞一次被限的端点。字段默认值（`types/provider.ts`）：`batchSize` 5、`batchConcurrency` 1、`requestInterval` 0.5 s。

**`autoFree`。** `createFallbackTranslator(['youdaoFree', 'bingFree', 'googleFree', 'deeplx'])`（`fallback.ts`）：源失败、条数不等或全空就换下一源；`isSourceUnavailable` 已在有道冷却期内以 info 日志跳过它。子源以 `{ ...proof, id: sourceId }` 调用，限速键为 `googleFree:googleFree`，批量、并发、间隔取 `autoFree` 自己的（10 / 1 / 0.3 s）。

**迁移。** `CURRENT_PROVIDER_VERSION` 现为 26。本变更不动服务商字段与默认值，不需要迁移。

**协议来源与清洁室。** 协议事实（端点、参数名、响应形状）来自本机实测与公开讨论（googletrans #268、Subtitle Edit #14015 与 PR #14050 的描述）；实现自行编写，不阅读也不复制第三方实现代码。

## Goals / Non-Goals

**Goals:**

- gtx 被限的网络里，谷歌免费源仍然可用；一集 600 条字幕的请求数从 600 降到 30（批量 20）或 120（默认批量 5）。
- 两条通道对用户透明：没有新设置，默认值不变；出问题时自动切换、自动恢复。
- 失效时快速让位：冷却期内不再发无谓请求，`autoFree` 不被拖慢。
- 不引入新依赖，不改变有道、必应、DeepLX 的行为。

**Non-Goals:**

- 不新增服务商、不新增字段、不迁移；不改 `googleFree` 的默认批量与 `autoFree` 的链顺序。
- 不做用户可见的通道开关；不持久化通道状态。
- 不轮换 `client` 标识、代理或 UA，不做指纹伪装或异常页绕过。
- 不集成 Google Cloud 官方 API（已有 `google` 服务商）；不处理超长单条文本（沿用 5,000 字符截断）。
- 本阶段不写代码。

## Decisions

### D1 · 两条通道与固定顺序（chrome 优先）

两条通道都在 `googleFree` 内部：

- **chrome 通道**：`GET https://translate.googleapis.com/translate_a/t?client=dict-chrome-ex&sl=…&tl=…&q=…&q=…`，一个请求多个 `q`，整批翻译。
- **gtx 通道**：现状不变，`translate_a/single?client=gtx`，逐条。

每个块（见 D2）先走 chrome 通道；该通道不可用（冷却中或探测被占用）或本块失败时改走 gtx 通道。顺序是模块内常量，不是设置项（已由维护者确认，2026-10-15）。

- 为什么 chrome 在前：该出口 IP 上 gtx 三天的每次探测都被限、chrome 全部成功；chrome 整批，请求数少一个数量级；gtx 在后意味着它只在 chrome 失败时才被碰，被限的通道不会每个进程都先吃一次 429。
- 为什么主机用 `translate.googleapis.com`：与 gtx 同主机，走同一 DNS 与代理路径，不需要新增代理或防火墙放行项；对照表明主机不是限流的判别因素，没必要引入 `clients5.google.com`。
- 为什么保留 gtx：两条通道互为备份（Google 可能单独封 `dict-chrome-ex` 或改协议）；现有用户已经在用 gtx；去掉它会让 chrome 成为单点。

备选：A「被限时把 `client` 从 gtx 换成 dict-chrome-ex，其余仍逐条」——最小（约 2–3 小时），但拿不到整批收益，仍是 600 个请求；C「新增服务商 `googleChromeFree`」——需要 `CURRENT_PROVIDER_VERSION` 26 → 27 与迁移，用户要在两个「谷歌」之间选择，否决；gtx 在前——更贴近现状，但被限的网络里每个进程都先吃一次 429。

### D2 · chrome 通道：请求构造与切块

- GET + 重复 `q`。`axios` 默认把数组参数序列化成 `q[]=`，服务端不认；因此查询串手工构造（`URLSearchParams` 逐个 `append`），拼进 URL 字符串后调用 `axios.get(url, config)`，这样测试里能看到精确 URL（现有 `scripts/test-free-translators.cjs` 就是替换 `axios.get` 来断言请求）。
- 一块 = 一个 HTTP 请求 = 一次 `acquire`。一块里编码后的查询串（含 `client`、`sl`、`tl`）不超过 6,000 字节，`q` 不超过 50 个，否则按原顺序切成多块。依据：实测 GET 到 16,216 B / 320 行都通过；取约 1/3 作预算，低于常见中间设备的 8 KB 请求行上限，并给将来的限制变化留余量。
- 单条编码后本身超过预算时单独成块，不拆行；单条文本先截断到 5,000 字符（沿用 `MAX_TEXT_LENGTH`）。字幕场景里单条通常不超过 130 字符，不会触发。
- 空串与全空白条目不进请求，原样放回原位置；整批都是空白则零请求（与 gtx 通道现状一致）。
- 不用 POST：实测可用（`client` 必须在 URL 查询里，放进表单体会被当成无 `client` 而 429），可以把字幕文本移出 URL；但 GET 已经过 200 多次验证、形态与 gtx 一致。POST 留作遇到 URL 长度问题时的备选。

### D3 · chrome 通道：响应解析与对齐

- 顶层必须是数组，长度等于本块发出的 `q` 个数。元素是字符串（显式 `sl`），或首元素为字符串的数组（`sl=auto` 的 `[译文, 检测语言]`）；其它形状都是协议异常。
- 译文按发送顺序填回非空条目的位置；不对译文做任何二次改写（弯引号是服务端行为，与 gtx 通道一致）。
- 长度不符、形状不符、任何一项译文为空（空串或全空白），都视为该通道本块失败（计入通道失败计数），该块改走 gtx 通道，不使用该响应里的任何一项。不做二分与逐条重试：负载测试的 120 个请求 0 错位，而 gtx 回退本身就是逐条。唯一的例外是仅因空项被拒绝的块，见下面「空项先在通道内重发一次」。
- 为什么「任何一项为空」而不只是「全空」：响应的每一项都对应一条非空白输入（空白条目不进请求），而服务对无法翻译的行返回原文——2026-10-15 对 18 种符号 / 标签行（`♪`、`...`、`-`、`?!`、`42`、`<i></i>`、`{\an8}`、`{\an8}♪`、`[music]`、`…`、emoji 等）的复测里，没有一项返回空串。所以空译文不是合法答案，而是降级答案：同日的实网冒烟里，一批 20 条的响应出现过 8 项空串、另 12 项正常；之后同样内容重发 5 次、拆成 10 / 12 / 15 条、倒序、`sl=auto` 都没有复现，说明是偶发的服务端部分失败。若只拒绝「全空」，这 8 条字幕会静默变成空行。
- **空项先在通道内重发一次**（2026-10-15 由维护者决定，原 OQ7）：仅因译文为空而被拒绝的块，先用同样的请求在 chrome 通道内重发一次；重发的响应有效就用它，这一块不算失败；重发的响应仍被拒绝、或重发的请求本身失败，才按上一条改走 gtx，且这一块在 chrome 上最多计一次失败。依据是那次事件不可复现：同样的 20 条重发 5 次、都是 0 空项，所以再问一次大概率就恢复；而在 gtx 被限的网络里（正是这条通道最有用的地方），不重发的代价是整批失败、保留原文，只能靠用户手动重翻。取舍：
  - 重发整块，而不是只补空项：补空项要把两次响应按位置混用，打破「整块有效或整块作废」的契约，位置映射与条数校验都要重写；整块重发只多一个请求，响应仍由同一个 `parseChromeResponse` 校验。
  - 只对空项重发：条数不符与形状异常没有证据表明是瞬时的，重发只会对异常的服务多发请求，仍然直接回退。
  - 只重发一次、不循环：最坏情况每块多 1 个请求；连续的降级答案由通道失败计数（连续 3 次 → 120 s）兜底。
  - 重发与其它请求一样先 `acquire`、响应取消，不产生日志（日志只记状态变化）；探测中的重发属于同一次探测，探测占用到重发结束才释放。
- 这条规则只用于 chrome 通道：该通道的合法答案从不为空有实测依据；gtx 通道的现有行为不改（该出口 IP 上 gtx 被限，无法取证它对符号行的返回，不能凭猜测改变现有语义）。
- 局限：该端点不回显原文，无法像有道那样校验内容对齐，只能校验条数。

### D4 · 通道健康与冷却

每条通道各有一份进程内状态 `{ failures, level, coolUntil, probing }`，不落盘：进程重启或网络切换后从干净状态开始（出口 IP 变了，旧状态没有意义）。时间一律取 `Date.now()`，测试用假时钟（与有道的做法一致）。

- **被限**：状态 429 或 403，且响应体含异常流量页标记（`unusual traffic`、`automated queries` 或 `/sorry/`，不区分大小写；响应体可能是字符串，也可能已被 `axios` 解析成对象）。冷却首次 10 分钟，之后每次再被限（含探测失败）翻倍，上限 60 分钟；一次成功清零。不含标记的 429 / 403 按「其它失败」处理，不触发长冷却。
- **其它失败**：网络错误、超时、其它 4xx / 5xx、协议异常（D3；一块在 chrome 上最多计一次，含空项重发）。连续 3 次 → 冷却 120 s；探测失败再冷却 120 s；一次成功清零。
- **不计入**：任务取消、`not supported language`（请求前的映射失败）。
- **探测**：冷却结束后只放行一个请求（真实的下一块）；探测进行时，该通道对其它并发调用视为不可用；占用标记在 `finally` 里释放，取消的探测不会卡住下一次。
- **数值依据**：上游报告被限「持续数分钟到数小时」，本机观察跨 3 天。10 分钟起，短封能较快恢复；60 分钟上限让「被封多天」时每小时只有 1 个探测请求。其它失败沿用有道的 3 次 / 120 s，保持一致。数值是内部常量，首版按反馈调整（OQ4）。

为什么分两档：异常流量页是 IP 信誉信号，几秒的重试越不过去；普通错误（断网、代理抖动）恢复快，短冷却即可。若 Google 改了页面文案，标记匹配失效，则退化为「其它失败」：最坏每 120 s 多一个探测请求，仍然安全。

### D5 · 块级通道切换与失败汇总

一个块先试 chrome，失败（含冷却中跳过）则试 gtx，每块最多切换一次、不循环。同一个块里两条通道的结果不混用：chrome 一块的结果要么整块有效、要么整块作废，作废后整块交给 gtx 逐条重做（仅因空项被拒绝的块，先在 chrome 内重发一次，见 D3）。gtx 对一个块是逐行请求，中途某行失败 → 该块失败，不回头再试 chrome。一块在两条通道都失败 → 整个调用以 `(network)` 错误失败，不返回部分结果，交给批级重试或 `autoFree`。

状态按块更新，所以同一次调用里：第 1 块 chrome 成功；第 2 块 chrome 被限，改走 gtx 并让 chrome 进入冷却；第 3 块直接走 gtx；结果按原顺序拼接。

### D6 · 两条通道都不可用与回退链集成

- 一块开始时若两条通道都处于冷却或探测占用，不发任何请求，立即抛出 `Google free translate failed (network): temporarily unavailable (both lanes cooling down, retry in N s)`。
- `googleFree.ts` 导出 `getGoogleFreeAvailability()`，形状与 `getYoudaoFreeAvailability()` 相同：仅当两条通道都不可用时 `available: false`，`retryAfterMs` 取两者剩余冷却中较小者（探测中为 0）。`fallback.ts` 的 `isSourceUnavailable('googleFree')` 据此以 info 级别跳过，文案 `cooling down (retry in N s)`，避免每个批次先失败一次再换源。
- 显式选用 `googleFree` 的用户：两条都冷却时每批立即失败（零请求），沿用现有的批失败语义：按「翻译重试次数」重试（每次先等 1 s、2 s…），用尽后保留原文并标记失败。请求数比今天少得多（被限的网络里每次重试现在都会再发请求），但批级重试的等待时间不变；要让这类任务更快失败，上层需要区分「不可重试的网络错误」，不在本变更范围内。

### D7 · 限速、超时、取消、代理

- 两条通道共用限速键 `googleFree:<providerId>`：每个 HTTP 请求（chrome 一块、chrome 空项重发、gtx 一行、探测、切换后的重发）前 `acquire`。`windowMaxRequests` 从此按请求数计，而不是按行数；提示与文档同步。
- chrome 通道专用 15 s 超时（实测 p95 约 1.1 s，320 行 GET 2.3 s；被限通道的挂起不该让每个块空等一分钟）。gtx 通道保持全局 60 s，不改变现状。
- 同一 `axios`（自动跟随 `proxyManager` 的全局代理）、同一浏览器式 UA，不新增请求头。
- 取消信号贯穿 `axios` 的 `signal` 与 `acquire` 的等待，抛任务取消错误，不计入通道失败，探测占用在 `finally` 释放。

### D8 · 错误分类与日志隐私

- 所有运行期失败都以 `Google free translate failed (network): ` 开头（见 Context「错误分类」：含 403 / 401 的消息会被当成配置错误而中止整个任务，带 `network` 才被排除）。测试直接断言 `isConfigurationError(error) === false`。`not supported language` 仍只用于目标语言映射失败，在发出任何请求前抛出。
- 响应体只用于标记匹配，不进入错误信息或日志；错误信息不含字幕原文。
- `logMessage` 只记录通道 id、状态类别（blocked / failure）、冷却秒数、恢复、块数与条数；不记 URL（GET 的 URL 含字幕原文）、原文、译文、响应体。每次状态变化一条日志（进入冷却 warning、恢复 info），不按批次刷屏；`autoFree` 的跳过由 `fallback.ts` 以 info 记录。

### D9 · 语言映射

沿用 `convertLanguageCode(x, 'google')`；源语言映射为空时发 `auto`；目标语言映射失败抛 `not supported language`，不发请求。本变更不改 `supportedLanguage` 的 Google 列。无效的 `tl` 会被服务端静默回显原文（实测），所以只发映射表内的码；不加「回显即失败」的检测，因为源语言与目标语言相同（如英 → 英）时回显是预期行为。

### D10 · 默认值、迁移与兼容

- `googleFree` 的字段与默认值不变（批量 5、并发 1、间隔 0.5 s、窗口 0），不迁移，`CURRENT_PROVIDER_VERSION` 保持 26；`autoFree` 链顺序不变，谷歌仍排第三。
- 默认批量 5 在 chrome 通道上就是整批 5 行 / 请求：600 行 = 120 个请求，约 1–2 分钟（推算）；批量 20 则 30 个请求、约 35 s（实测）。是否把默认批量提到 20 留给后续变更（OQ3）：它需要「只升级仍等于旧默认值的字段」式的迁移，而且 `autoFree` 子源用的是 `autoFree` 自己的批量（10）。
- 回滚：回退代码即可；没有持久化状态、没有配置变更。

### D11 · 测试策略

CI 与单测一律不访问真实网络，沿用 `scripts/test-free-translators.cjs` 的 mock `axios`（替换 `axios.get`）与 TypeScript 转译手法，新增 `scripts/test-google-free.cjs`：

- 纯函数：查询串（重复 `q`、无 `q[]`、`&`、`#`、`+`、`%`、换行、emoji 的编码）、切块（50 行、6,000 字节、超长单条、空白位置）、解析（两种形状与各类异常形状）、异常页识别（429 / 403 + 标记为被限；无标记的 429 / 403、200 都不是）；
- 翻译器：chrome 成功时 gtx 零请求；chrome 被限 → 本块走 gtx、chrome 冷却、后续块直走 gtx；反向（gtx 被限、chrome 正常，即实网证据里的方向）；块级混合与顺序；条数不符、形状异常 → 直接走 gtx（只发 1 个 chrome 请求）；任一项为空（含 20 条里 8 项为空的实网形状）→ 同样的请求重发一次，重发有效则采用（0 个 gtx 请求、不算失败），重发仍有空项 → 走 gtx 且只计一次失败，gtx 也被限时调用失败而不是返回空行；重发的限速、取消与探测语义；`sl=auto`；空白行还原；两条都冷却 → 零请求 + `(network)`；
- 健康：假时钟下 10 / 20 / 40 / 60 / 60 分钟退避、3 次 / 120 s、单探测与并发调用方、成功清零、取消不计入且探测占用释放、`getGoogleFreeAvailability()` 的取值；
- 限速键共用、超时、取消、错误分类（带 `(network)`、`isConfigurationError` 为 false、`not supported language` 零请求）、日志隐私（不含字幕文本与 URL）；
- 回退链：真实 `fallback.ts` + 假兄弟源，谷歌冷却期被跳过、恢复后重新使用。

实网只做手动冒烟（见 tasks 的 Verification），总量约 100 次请求以内，遇到第一个 429 就停。

## Risks / Trade-offs

- [非官方、未文档化的端点，可能随时变化、被限或下线；上游 Subtitle Edit 在 2026-08 遇到 gtx 被限就是例证，说明两个端点都不能当作稳定接口] → 双通道互为备份；冷却 + 探测；回退链兜底；文档如实披露「不承诺可用性」。
- [公地效应：更多应用使用同一 `client`，桶被集体拉黑] → 整批把请求数降一个数量级（600 行 30 个请求对 600 个）；保持默认 0.5 s 间隔；被限即冷却至少 10 分钟，不抢；不轮换标识。
- [证据只来自单一出口 IP；gtx 被限的起点与成因未知，不排除调研期间的探测触发，也可能早已存在] → 记录观测时间线；反向回退用假服务测试覆盖；在未被限的网络补做 gtx 通道与反向回退的实网冒烟（tasks 7.3）。
- [chrome 通道译文质量未与 gtx 对照] → 样例正常；定位是「gtx 被限时的可用通道 + 整批加速」，文档不声称质量等同；gtx 恢复后补一次抽样对比。
- [条数对齐只能校验数量，不能校验内容] → 负载测试 120 个请求全部对齐；条数不符、形状异常、任一项为空 → 回退 gtx；Google 改协议时由单测夹具与手动冒烟发现。偶发的部分空串（2026-10-15 实网冒烟约 50 个 chrome 请求里见到一次）先在通道内重发一次（D3）；仍有空项才整块作废，不留空行。
- [GET 的 URL 含字幕原文] → 与 gtx 通道同等暴露；不记录 URL；文档披露；POST 是备选（D2）。
- [`axios` 数组序列化成 `q[]=`] → 手工构造查询串 + 精确 URL 断言。
- [无效 `tl` 被静默回显] → 只发映射表内的码，映射失败抛错（D9）。
- [两条通道共享同一 IP 信誉：若 Google 改为按 IP 总量限流，双通道不再有额外保护] → 接受；此时两条通道都冷却，`(network)` 错误交给回退链。
- [探测请求会把一块真实字幕发给被限通道] → 探测失败的块立即改走另一条通道，用户无感；每个冷却周期只有一次。
- [`windowMaxRequests` 改为按请求计，而不是按行] → 默认 0（不启用）；只影响手动设置了窗口上限的用户，且方向是更宽松；提示与文档同步。
- [合规：非官方接口可能违反服务条款] → 与既有 gtx 同级；不绕过任何访问控制，不轮换、不伪装；文档披露。

## Migration Plan

1. 随新版本发布：无迁移、无功能开关（通道顺序是单个常量）。
2. 回滚：回退代码即可，没有持久化状态。
3. 文档与提示文案随版本同步；`changelog.md` 按发布流程补充。
4. 顺序维护：若日后 chrome 通道被限而 gtx 恢复，通道健康会自动绕开；需要长期翻转时改常量并发版。

## Open Questions

- **OQ1 · 通道顺序（已确认：chrome 优先，2026-10-15）。** 备选是 gtx 优先；翻转只需改一个常量，通道健康会自动绕开被限的通道。
- **OQ2 · 范围（已确认：方案 B，双通道，2026-10-15）。** A 最小版、C 新服务商均未采用，理由见 D1。
- **OQ3 · 默认批量是否从 5 提到 20。** 推荐作为后续独立小变更：需要迁移仍等于旧默认值的字段；而且它只影响显式选用谷歌的用户，`autoFree` 子源用的是 `autoFree` 自己的批量（10）。
- **OQ4 · 冷却数值**（被限 10 → 60 分钟，其它 3 次 / 120 s）是首版取值；用日志里的冷却次数与用户反馈校准。
- **OQ5 · `autoFree` 链里谷歌的位置。** chrome 通道能整批后，谷歌可能比必应快，但质量未对照；放到必应之前是产品决策，需要质量对比后另议，本变更不动。
- **OQ6 · UA 字符串（Chrome/131）偏旧。** 上游把更新 UA 当作「卫生」措施，但证据不足以证明 UA 影响限流；免费源共用同类浏览器式 UA，要改应作跨源的独立小变更，本变更不动。
- **OQ7 · 部分空串的处理（已确认：整块在 chrome 通道内重发一次，2026-10-15）。** 备选是只补发空的那几项（会让两次响应混用，打破「整块有效或整块作废」，见 D3），以及首版那样不重发（gtx 被限的网络上该批失败、保留原文，因为 `translateRetryTimes` 未设置时为 0）。实网只见到 1 次（约 50 个 chrome 请求里 1 次）；若日志里「empty」类的通道失败仍然频繁出现，再议是否补空项或多重发。
