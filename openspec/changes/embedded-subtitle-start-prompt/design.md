## Context

「优先使用内封字幕」是任务级布尔 `useEmbeddedSubtitles`：只有显式 `false` 才强制语音识别，缺省（含旧任务、配方、自动化提交）都按「使用」处理（`shouldUseEmbeddedSubtitles`）。流水线对每个待转写的文件做同一件事：配对字幕 → 直接用；否则若开关开启且容器可能内封字幕，就用 `ffmpeg -i` 探测，取**第一条**文本字幕轨直接抽成 SRT，失败再回落到语音识别（`fileProcessor.ts`）。内封字幕不经 AI 断句、不做文稿匹配，字幕保持视频原文。

界面上，这个开关 3.8 时在工具栏上，3.9 起收进了「字幕格式」气泡的底部（`OutputFormatControl`）。工具栏现在是 9 个控件的不换行一行，已无处可放。

开始任务有三个入口（任务页 `TaskControls`、向导 `TaskWizard`、任务页的重试），共用同一个状态机 `useTaskSubmission().submit()`：`validating → confirming → submitting`，其中校验会在云端上传确认前后各跑一次，提交载荷由 `taskSubmissionKey` 生成幂等的 `requestId`。云端上传确认（`useTaskCloudConsent`）已经是「开始前弹确认、可勾选不再提醒、取消即终止」的现成先例。

## Goals / Non-Goals

**Goals:**

- 用户在点「开始」、而内封字幕**确实会生效**的那一刻得到一次告知与选择；之后知道去哪里调整。
- 探测的耗时用户感觉不到：典型情形几乎无感，最坏情形有硬上限，失败时回到改动之前的行为。
- 开关换到高级选项后仍然是同一个任务级布尔，快照、配方、自动化与流水线一行不改。

**Non-Goals:**

- 按字幕语言挑选轨道（流水线仍取第一条文本轨）。
- 添加文件时预探测并在行上打徽标、「高级选项」按钮上的指示点（第二阶段）。
- 自动化 / CLI / MCP 的同类询问；任务字段、快照与配方 schema 的任何变化。
- 版本号与 `Changelog/`（发版时写）。

## Decisions

**1. 开关放进「高级选项 › 转写」顶部，不放回工具栏。**
工具栏放不下，再挤一个控件会让 1024 宽度下的其余控件被截断。高级选项的「转写」分区正是它的语义归属（字幕从哪来：识别还是提取），任务页与向导共用同一个 `AdvancedSheet`，所以向导也第一次有了这个开关。可见性的损失由决策 2 补回：在它会生效的时刻主动问。
备选：保留在气泡里改个说明——否决：根因是它藏得深而不是文案；备选：工具栏加图标按钮——否决：同样是在挤占一个只对部分视频有意义的常驻位置。

**2. 在「开始」时探测并询问，不做常驻徽标。**
用户的意图发生在点「开始」的那一刻；此时列表已定、配置已定，问题也最具体（「这个视频里有字幕」）。询问只在命中时出现，没有内封字幕的列表不会多任何提示。常驻徽标需要在添加文件时预探测并维护每行状态，代价与状态面都大得多，留作第二阶段。

**3. 探测复用 `ffmpeg -i`，调度与探测分开。**
探测本身沿用流水线已经在用的做法（`ffmpeg -hide_banner -i <文件>`，解析 stderr 里的 `Subtitle:` 行；仓库只带 `ffmpeg-static`，没有 ffprobe）。为了可测，把 `probeEmbeddedSubtitles` 从 `audioProcessor.ts`（依赖 `storeManager`、`fluent-ffmpeg`、一大串模块）搬到只依赖 `ffmpeg-static` 与 `child_process` 的 `embeddedSubtitleProbe.ts`，`audioProcessor.ts` 原样再导出，`fileProcessor.ts` 的调用不变；新增可选的 `AbortSignal`（中止即终止子进程并返回空，且不记警告）与 `windowsHide: true`（Windows 上批量 spawn 控制台程序会闪窗；仓库里其它直接 `spawn` 的地方都已设置）。
调度是纯逻辑 `scanForEmbeddedSubtitles(filePaths, { probe, concurrency, budgetMs })`：去重、按容器扩展名过滤、固定大小的工作池、首个命中即 `abort` 其余、整体预算到点即 `abort`，返回 `found | none | unknown`。`probe` 由调用方注入，所以并发、早退、预算、中止都能用假探测函数确定性地测，真实 ffmpeg 另有一条集成测试。

**4. 性能预算：实测数据与取值。**
在 ffmpeg 6.0、Apple Silicon、SSD、热缓存下实测：单文件探测约 11–12 ms，与文件大小无关（只读容器头）；首次 spawn 约 58 ms，含 TS 开销约 30 ms；50 个无命中文件，串行 556 ms、4 并发 155 ms、8 并发 104 ms；第 3 个文件命中时提前结束只需 23–34 ms。典型的几十个文件几乎无感。风险环境是 Windows（进程创建与杀毒软件）以及机械盘 / NAS / 休眠中的磁盘：单次探测可能是数十到数百毫秒。所以取并发 4（收益在 4 之后基本饱和，同时不挤占磁盘）、整体预算 1000 ms，到点放弃。渲染进程这边再对 IPC 加一道略长于预算的超时（1500 ms），主进程万一没响应，界面也不会挂住。
超时与出错一律**失败开放**：不弹窗、不报错、任务照常开始。这与改动之前完全一致（开关开启则静默使用内封字幕），最坏情形就是回到现状，不会比现状更差。

**5. 与就绪校验并行，在校验之后、云端上传确认之前询问。**
`submit()` 在启动第一次 `validateTaskStart` 的同时启动探测，两者互不依赖，用户感受到的等待是两者中较长的一个而不是之和。校验失败就直接返回校验错误，不为一个无法开始的任务弹窗；校验通过后再等探测结果（通常早已就绪）。询问放在云端上传确认之前，因为用户选择「改用语音识别」后才可能需要上传确认；已经把选择写进本次提交的载荷，随后的第二次校验也基于最终载荷。「开始」按钮在整个过程中保持 `starting`（与现有的 `validating / confirming` 阶段一致）。
询问只改本次提交的 `snapshot.formData.useEmbeddedSubtitles`；它是载荷的一部分，所以 `taskSubmissionKey`（幂等键）随之变化，选择不同就是不同的提交，选择相同的重试仍复用同一个 `requestId`。提交被接受后，`onTaskDispatched(outcome.snapshot)` 拿到的是实际生效的载荷：选了「改用语音识别」时快照里是 `false`，任务页按既有规则（`isPinnedTaskConfigSnapshot`）切到只读快照并显示「强制听写」，重试也复用它。

**6. 选择只对本次生效，「记住」才写入，且只写两处。**
对话框的两个选择按钮默认只改本次提交的载荷，不碰表单，不写默认配置，与云端上传确认一致（用户已确认）。勾选「记住我的选择，不再提示」后才写：`settings.embeddedSubtitlePrompt = false`（以后不再弹），以及默认配置里的 `useEmbeddedSubtitles`（经既有的 `updateTaskDefaults` 补丁通道，只写这一个键，`useEmbeddedSubtitles` 不是逐任务键）。两处缺一不可：只写前者，选了「改用语音识别」的人下次会被静默用回内封字幕，与「记住我的选择」相悖；只写后者，提示仍会弹。
**与 `task-defaults-memory` 的关系。** 该规格（`sync-task-defaults-on-edit`，尚未归档）规定默认配置只来自可编辑的任务页，向导与开始任务本身都不写。这里的写入是用户在对话框里**显式勾选**的指令，而非「开始任务」或「同步表单」的副作用，范围只有一个键，向导里其它参数仍然不写。我认为这与那条规则的本意（防止向导 / 旧工程的整份配置冲掉默认值）不冲突，但字面上是一处例外，所以在该规格的对应要求末尾补了一句例外说明，并在本变更的规格里写成独立要求，避免两份规格各说各话。
写入是尽力而为：失败只吞掉，本次选择照常生效（与云端上传确认一致）。点「取消」绝不记住。
**新用户的默认值。** 出厂默认配置里 `useEmbeddedSubtitles` 为 `true`，设置里不写 `embeddedSubtitlePrompt`（缺省即提示），所以全新安装是「优先使用内封字幕」开、「记住」关；对话框里的复选框每次都从不勾选开始。「高级选项」里的「开始前提示我选择」是 `embeddedSubtitlePrompt` 的正向写法，与「记住」互为反面：勾选 = 会询问，不勾 = 已记住。这两项只有用户的显式操作才会改写——在「高级选项」里拨动开关会像其它参数一样被记为默认值，所以一台试过「关闭 + 记住」的机器上看到的「开关关、提示未勾」是它自己的存档，不是新用户的默认。出厂值由 `EmbeddedSubtitleDefaults.test.ts` 与端到端的第 0 步锁定。

**7. 不弹窗的情形集中在入口处判断。**
`useEmbeddedSubtitles === false`（已强制语音识别）、`embeddedSubtitlePrompt === false`、`typeDef.needsModel` 为假（翻译字幕类）、没有可探测的文件——在发出 IPC 之前就返回，零开销。重试经 `submit(input, { promptEmbeddedSubtitles: false })` 关闭：重试要复现原任务的行为，旧任务快照里没有该字段就等于「使用」，再问一次只会让人困惑。配置已固定的任务页（`configSnapshot` 存在，页面只读）同样关闭，经 `TaskControls` 的 `promptEmbeddedSubtitles` 入参传入：主进程的 `persistTaskSubmission` 在已有固定快照时沿用快照而不是本次提交的 `formData`，此时问了也不会被采纳，反而误导；第一次开始时快照还不存在，选择照常写进快照，之后每次开始都沿用它。自动化 / CLI / MCP 与在线下载的自动衔接不经 `useTaskSubmission`，天然不弹窗。`?autostart=1` 是用户发起的开始，照常询问。

**8. 探测哪些文件，与流水线一致、再保守一点。**
流水线只有在「不是字幕文件、没有可用的配对字幕、开关开启、容器可能内封字幕」时才会探测。这里沿用 `validateTaskConfigReady` 里 `needsTranscription` 的同一个谓词（非字幕文件且没有 `providedSubtitlePath`），再由主进程按 `canHaveEmbeddedSubtitle` 过滤容器。只有**文本**字幕轨算命中（流水线只取 `isText` 的轨，位图轨提取不了）。向导里的文件列表同样带 `providedSubtitlePath`，规则相同。

**9. 新 IPC `findEmbeddedSubtitles`，不进自动化目录。**
`{ filePaths }` → `{ status, hit?, checked, candidates, elapsedMs }`，`hit` 只含文件路径与文本轨的 `{ language?, codec }`。它是界面专用的内部通道，通过 `automation/handlers` 的注册门面注册，但不加进 `automation/catalog.ts`，所以 CLI / MCP 不会暴露它。入参只接受字符串数组，去重并限制数量，防止异常大的列表。

**10. 对话框。**
沿用 `useTaskCloudConsent` 的结构（`AlertDialog`、`pending` 引用、卸载时以取消收尾），另加 `Checkbox`。内容：标题「检测到视频内封了字幕」；命中的文件名与轨道（`语言 · 编码`，语言用 `Intl.DisplayNames` 转成本地语言名，不认识的代码原样显示）；两个选项各一句话的后果说明（使用内封字幕：直接提取、几秒完成、不做语音识别、字幕保持视频原文、不做 AI 断句与文稿匹配、多条时取第一条；改用语音识别：重新听写、更慢、语言与断句按设置处理）；说明混合列表里其它带字幕的视频同样处理；提示之后可在「高级选项 › 转写」里调整。主按钮是「使用内封字幕」（与默认行为一致）。轨道最多列出 3 条，其余用「，另有 N 条」概括，免得一部多语种电影把句子撑成一堵墙。
「取消」与 Esc 终止这次开始（`AlertDialog` 不响应遮罩点击，与云端上传确认一致）。选择一旦开始落实——正在写入「记住」的那几十毫秒——Esc 不再取消，否则会出现任务被取消而默认值已经写下的矛盾；此时按钮与复选框也一并置灰，连点只算一次。

**11. 高级选项里的控件独立成组件。**
`EmbeddedSubtitleControl` 由 `enabled` / `onEnabledChange` 受控地呈现任务级开关，`AdvancedSheet` 把后者接到 `form.setValue('useEmbeddedSubtitles', …, { shouldDirty: true })`——与原来气泡里的写法完全一致，所以任务页上的实时记忆照常工作；复选框「开始前提示我选择」是全局设置，由控件自己负责：挂载时 `getSettings`（读不到按「提示」处理），改动时乐观更新并 `setSettings`，失败回滚（较新的改动不会被较早的失败覆盖）。独立成组件是为了能单独测试，不必渲染一千多行的 `AdvancedSheet`；`AdvancedSheet` 这一层的接线另有一条用真实表单渲染的测试。
顺手删除了气泡里引用不存在的 `configBar.embeddedSubtitlesTip` 的那段，新文案准确描述「提取」而不是「封装」。`configBar.embeddedSubtitles` 保留并被新控件复用，只读快照栏也仍在用（「优先使用内封字幕：已关闭，强制听写」读起来依然通顺）；中文由「优先内封字幕」改为「优先使用内封字幕」，英文不变。

## Risks / Trade-offs

- [慢速存储上放弃探测] → 预算到点即回到改动之前的行为；这是有意的取舍——宁可少问一次，也不能让「开始」变慢。第二阶段的添加时预探测可以把这部分成本移出点击路径。
- [字面上违背 `task-defaults-memory` 的「向导 / 开始任务不写」] → 例外限于用户显式勾选、一个键，已在两份规格里写明，并由测试锁定（未勾选与取消都不写；向导里勾选只写这两项）。
- [混合列表] → 选择按整个任务生效，没有字幕轨的文件无论如何走语音识别；对话框用一句话说明。若用户选「改用语音识别」，带字幕的文件也要听写——这正是他的选择。
- [取第一条文本轨，不看语言] → 与现状一致，对话框列出全部轨道让用户知情；按语言选轨留作单独改动。
- [命中即停，不统计个数] → 对话框描述第一个命中的文件即可；统计需要探测全部，与「不卡顿」冲突。
- [探测与流水线各探一次] → 命中的文件会被探测两次（点击时一次、流水线里一次），每次约 10 ms 量级，不值得为此做缓存与失效逻辑。
- [Windows 上批量 spawn] → `windowsHide: true` 避免闪窗；杀毒软件拖慢进程创建时由 1 秒预算兜底。
- [云端转写引擎：选了「使用内封字幕」之后仍会遇到云端上传确认] → 有意保留。确认文案说的是「提取每个文件的音轨并上传」，而这里省不得：列表里没有内封字幕的文件仍要上传；流水线在提取失败（轨道损坏、没有字幕条目）时会回落到语音识别，音频仍可能上传。隐私确认不能建立在「大概不会上传」的猜测上。只影响选了云端引擎的用户；单文件且已确认命中时跳过确认可作为后续优化，需要先让提取结果可预知。
- [`?autostart=1` 会弹窗] → 这是用户发起的开始，且选择同样影响结果；弹窗期间自动开始的 ref 已经置位，不会重复触发。
